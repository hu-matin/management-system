# تسک عملی طراحی UI/UX و توسعه Frontend

**شرکت دانش گستر هوشمند سلامت**  
**موضوع:** سامانه مدیریت درخواست‌های سازمانی  
**زمان ارسال تسک:** دوشنبه (تاریخ دقیق در پیام ارسال مشخص می‌شود)  
**آخرین مهلت تحویل:** چهارشنبه همان هفته، ساعت ۱۷:۰۰ به وقت تهران  
**زمان پیشنهادی:** حدود ۸ تا ۱۲ ساعت برای بخش اصلی؛ چالش امتیازی کاملاً اختیاری است.

## ۱. هدف پروژه

یک اپلیکیشن تحت وب برای ثبت، مشاهده، جست‌وجو، فیلتر و ویرایش درخواست‌های سازمانی طراحی و پیاده‌سازی کنید. این تمرین برای سنجش توانایی شما در **طراحی رابط کاربری از صفر** و **پیاده‌سازی Frontend متصل به REST API** است. توسعه Backend لازم نیست؛ سرویس Mock API همراه این تسک ارائه شده است.

## ۲. طراحی UI/UX با Figma

- طراحی صفحه داشبورد و فهرست درخواست‌ها.
- طراحی فرم ایجاد و ویرایش درخواست و نمای مشاهده جزئیات.
- طراحی حداقل دو نسخه **دسکتاپ و موبایل**؛ استفاده درست از Auto Layout، Component و Variant در Figma.
- پشتیبانی کامل از زبان فارسی و راست‌به‌چپ (RTL)، رعایت خوانایی، سلسله‌مراتب بصری و اصول اولیه دسترس‌پذیری.
- طراحی حالت‌های Loading، Empty، Error، Success و خطاهای اعتبارسنجی فرم.
- ارائه توضیح کوتاه درباره تصمیم‌های مهم UI/UX.

## ۳. توسعه Frontend

**فناوری مجاز:** HTML، CSS و JavaScript خالص **یا** React.js **یا** Next.js. ابزارهای CSS مانند Tailwind اختیاری‌اند.

**امکانات الزامی:**

1. **داشبورد:** نمایش آمار کل، جدید، در حال بررسی و تکمیل‌شده با دریافت از API.
2. **فهرست درخواست‌ها:** نمایش داده‌های API، جست‌وجوی عنوان، فیلتر اولویت و وضعیت، صفحه‌بندی و مشاهده جزئیات.
3. **ثبت درخواست:** فرم شامل عنوان، توضیح، نام درخواست‌دهنده و اولویت؛ اعتبارسنجی و ارسال به API.
4. **ویرایش درخواست:** ویرایش اطلاعات و تغییر وضعیت؛ انعکاس نتیجه موفق در فهرست و داشبورد.
5. **حالت‌های رابط کاربری:** Loading، خطا، فهرست خالی، ثبت موفق و مدیریت خطای API.
6. **ساختار کد:** کامپوننت قابل استفاده مجدد، جداسازی منطق درخواست‌های HTTP از UI و خوانایی کد.

### الزام Responsive (اجباری)

- رابط کاربری در ابعاد **۳۶۰ پیکسل موبایل**، **۷۶۸ پیکسل تبلت** و **۱۴۴۰ پیکسل دسکتاپ** باید صحیح و قابل استفاده باشد.
- از اسکرول افقی ناخواسته، شکستن متن، هم‌پوشانی عناصر و دکمه‌های غیرقابل لمس جلوگیری شود.
- فهرست درخواست‌ها باید برای موبایل **راهکار مناسب و قابل استفاده** داشته باشد (برای مثال تبدیل جدول به کارت یا اسکرول کنترل‌شده با حفظ دسترسی به اطلاعات اصلی).
- طراحی و پیاده‌سازی نهایی باید با یکدیگر منطبق باشند؛ صرف کوچک‌کردن نسخه دسکتاپ قابل قبول نیست.

## ۴. ارتباط با Fake API (اجباری)

در پوشه `mock-api` یک REST API قابل اجرا با داده‌های نمونه وجود دارد؛ می‌توانید آن را با Docker یا Python طبق `README_FA.md` اجرا کنید. **تمام عملیات دریافت، ثبت و ویرایش اطلاعات باید از طریق این API باشد.** استفاده از آرایه ثابت یا LocalStorage به‌عنوان منبع اصلی داده پذیرفته نیست.

آدرس محلی API پس از اجرا: `http://127.0.0.1:8000`

| درخواست | مسیر | کاربرد |
|---|---|---|
| GET | `/api/stats` | آمار داشبورد |
| GET | `/api/requests` | فهرست، جست‌وجو، فیلتر و صفحه‌بندی |
| GET | `/api/requests/{id}` | جزئیات یک درخواست |
| POST | `/api/requests` | ثبت درخواست |
| PATCH | `/api/requests/{id}` | ویرایش درخواست و تغییر وضعیت |

**نمونه جست‌وجو و فیلتر:**

`GET /api/requests?q=دسترسی&status=new&priority=high&page=1&page_size=10`

**فیلدهای درخواست:**
- `id`: شناسه؛ عدد
- `title`: عنوان درخواست
- `description`: توضیحات
- `requester`: نام درخواست‌دهنده
- `priority`: یکی از `low`، `medium`، `high`
- `status`: یکی از `new`، `in_progress`، `completed`
- `created_at`، `updated_at`: تاریخ و ساعت ISO 8601
- `version`: شماره نسخه رکورد (برای چالش اختیاری)

**توجه:** بعد از Refresh، تغییرات ثبت‌شده باید از API خوانده شوند و همچنان قابل مشاهده باشند. برای جزئیات درخواست‌ها به فایل `docs/API_CONTRACT_FA.md` مراجعه کنید.

## ۵. چالش امتیازی پیشرفته (اختیاری؛ تا ۱۵ امتیاز اضافه)

### مدیریت ویرایش هم‌زمان و بازگردانی تغییرات (Optimistic UI + Conflict Handling)

فرض کنید دو کاربر یا دو تب مرورگر یک درخواست را هم‌زمان باز کرده‌اند. یکی از آن‌ها رکورد را ویرایش می‌کند و دیگری تلاش می‌کند همان نسخه قدیمی را ذخیره کند.

در پیاده‌سازی امتیازی:

1. هنگام دریافت درخواست، مقدار `version` را نگه دارید.
2. هنگام `PATCH`، فیلد `expected_version` را با نسخه‌ای که دریافت کرده‌اید ارسال کنید.
3. اگر سرور **409 Conflict** برگرداند، داده قدیمی را بی‌صدا جایگزین نکنید؛ به کاربر پیام قابل فهم بدهید و راهی برای مشاهده یا بارگیری نسخه جدید فراهم کنید.
4. برای تغییر وضعیت، **Optimistic UI** پیاده‌سازی کنید؛ تغییر را بلافاصله نشان دهید و اگر درخواست شکست خورد، رابط را به وضعیت قبلی برگردانید (Rollback).
5. خطای شبیه‌سازی‌شده **503** را نیز مدیریت کنید؛ نحوه آزمایش در مستند API آمده است.

این بخش **الزامی نیست** و تکمیل‌نکردن آن از امتیاز بخش اصلی کم نمی‌کند.
