# قرارداد REST API آزمایشی — راهنمای داوطلب

نسخه Mock API: `1.0.0`  
Base URL: `http://127.0.0.1:8000`  
مستندات تعاملی Swagger: `http://127.0.0.1:8000/docs`

**دقت کنید:** این API واقعی برای تمرین است، اما Backend تولیدی، احراز هویت و داده واقعی ندارد. دیتابیس آن SQLite محلی است و تغییرات در اجرای بعدی باقی می‌مانند.

## وضعیت و اولویت

| مقدار API | برچسب نمایشی پیشنهادی |
|---|---|
| `new` | جدید |
| `in_progress` | در حال بررسی |
| `completed` | تکمیل‌شده |
| `low` | کم |
| `medium` | متوسط |
| `high` | زیاد |

## GET /api/health

```json
{"ok": true}
```

## GET /api/stats

```json
{"total": 16, "new": 6, "in_progress": 5, "completed": 5, "open": 11}
```

> مقادیر فوق صرفاً مثال هستند؛ با ایجاد یا تغییر درخواست‌ها تغییر می‌کنند. آمار واقعی باید از API خوانده شود.

## GET /api/requests

Query parameters:
- `q`: جست‌وجو در عنوان یا نام درخواست‌دهنده؛ اختیاری
- `status`: `new` یا `in_progress` یا `completed`؛ اختیاری
- `priority`: `low` یا `medium` یا `high`؛ اختیاری
- `page`: عدد صحیح مثبت، پیش‌فرض `1`
- `page_size`: عدد از `1` تا `50`، پیش‌فرض `10`

مثال: `GET /api/requests?q=دسترسی&status=new&page=1&page_size=5`

شکل پاسخ:

```json
{
  "items": [
    {
      "id": 1,
      "title": "درخواست دسترسی به گزارش‌ها",
      "description": "نیاز به سطح دسترسی مشاهده گزارش‌های ماهانه دارم.",
      "requester": "سارا احمدی",
      "priority": "high",
      "status": "new",
      "created_at": "2026-11-14T08:20:00Z",
      "updated_at": "2026-11-14T08:20:00Z",
      "version": 1
    }
  ],
  "total": 1,
  "page": 1,
  "page_size": 5,
  "total_pages": 1
}
```

## GET /api/requests/{id}

پاسخ 200: آبجکت درخواست با همان فیلدهای بالا.  
پاسخ 404: درخواست پیدا نشد.

## POST /api/requests

بدنه (JSON):

```json
{
  "title": "نیاز به دسترسی جدید",
  "description": "دسترسی مشاهده داشبورد برای کاربر جدید لازم است.",
  "requester": "نازنین حسینی",
  "priority": "medium"
}
```

پاسخ **201 Created**: آبجکت ایجادشده با شناسه، تاریخ‌ها و `version: 1`.

الزام اعتبارسنجی: `title` بین ۳ تا ۱۲۰ کاراکتر؛ `description` بین ۵ تا ۲۰۰۰؛ `requester` بین ۲ تا ۱۰۰. مقدارهای اولویت و وضعیت باید از enum مجاز باشند. در غیر این صورت 422 برگردانده می‌شود.

## PATCH /api/requests/{id}

برای ویرایش ساده:

```json
{"status":"in_progress"}
```

یا ویرایش چند فیلد:

```json
{"title":"عنوان ویرایش‌شده","priority":"high"}
```

پاسخ 200: آبجکت به‌روزشده با افزایش `version`.

### چالش پیشرفته: 409 Conflict

برای جلوگیری از رونویسی ناخواسته رکورد قدیمی، `expected_version` را بفرستید:

```json
{"status":"completed","expected_version":1}
```

اگر نسخه فعلی سرور تغییر کرده باشد، پاسخ **409 Conflict** با شکل زیر خواهد بود:

```json
{
  "detail": {
    "code": "version_conflict",
    "message": "This request was updated by someone else; reload latest data.",
    "current": {"id": 1, "title": "...", "version": 2}
  }
}
```

راه ساده آزمایش: در دو تب مقدار `version` یک درخواست را بخوانید. در یکی آن را با `expected_version` ذخیره کنید؛ در تب دوم دوباره با نسخه قدیمی ذخیره کنید. تب دوم باید 409 دریافت کند.

### چالش پیشرفته: 503 شبیه‌سازی‌شده

برای آزمایش Rollback، هنگام `PATCH` هدر زیر را اضافه کنید:

`X-Mock-Fail: 1`

این درخواست با **503 Service Unavailable** شکست می‌خورد و داده در دیتابیس تغییر نمی‌کند. این هدر فقط برای آزمایش است و در درخواست‌های عادی نباید فرستاده شود.

## کدهای پاسخ مهم

| کد | مفهوم |
|---|---|
| 200 | درخواست موفق |
| 201 | ایجاد موفق |
| 404 | درخواست موجود نیست |
| 409 | ویرایش با نسخه قدیمی (اختیاری) |
| 422 | داده ورودی نامعتبر |
| 503 | خطای تستی سرویس (اختیاری) |

## راهنمای CORS و استقرار

برای توسعه محلی، Originهای `localhost` و `127.0.0.1` با هر پورت مجازند. برای Originهای دیگری که روی یک سرور شخصی استقرار داده شده‌اند، می‌توان متغیر محیطی `CORS_ORIGINS` را به صورت فهرست جداشده با ویرگول تنظیم کرد. **به دلیل نداشتن احراز هویت، سرویس آزمایشی را بدون محدودسازی دسترسی روی اینترنت عمومی منتشر نکنید.**
